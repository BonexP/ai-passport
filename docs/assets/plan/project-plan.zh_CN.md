# 项目规划：FoloToy AI Passport 集大成固件

范围：基于 `FoloToy/ai-passport` 基线（ESP-IDF 5.5.3）的自定义固件。
状态：P1 已完成。存储、开机遍历、状态页、预设注入与 SoftAP 配网均已实现，主机测试与固件构建通过；2026-10-31 上板实测通过烧录、配网、提交后联网与长按菜单各测试页。配网仍有三项未测，见 `task-breakdown.zh_CN.md`。P2 进行中：统一编译期配置、每 profile 坐标与地点名、SNTP 校时、HTTPS 传输、天气页与离线快照已实现并有主机测试；天气页与配网新增的经纬度/地点名字段尚未上板实测。P5（AMD Radeon Cloud 用量页，见 §4.5）进行中：传输层、
编译期 key、用量解析与显示逻辑已实现并有主机测试；多数据源 worker 与页面本体也已实现，只剩上板实测。
用量记录只活在本轮
会话的 RAM 里：不写 NVS 快照，因为额度在北京时间 0 点归零，隔夜的副本不是"旧"而是"错"。
实施顺序排在 P3 之前。
调研日期：2026-10-27，对应上游 `main` 提交 `006c227`。AMD Radeon Cloud API 调研：2026-11-10，对应文档最后更新 2026-11-03。

结论先行：功能集在不依赖任何外部辅助服务的前提下可行。唯一的硬约束是内存——本板
无 PSRAM，所有功能争抢约 320 KB 内部 SRAM。这个约束决定的是实施顺序和并发方式，
不是能不能做。

## 1. 目标

一个固件，覆盖五件事：

1. 多地点 Wi-Fi profile 与自动漫游（家里、公司、其他）。
2. 固定自选表的股票行情。
3. 当前地点的天气。
4. 局域网已知端点健康检查与 mDNS 服务发现。
5. 自己 API key 对应的 AMD Radeon Cloud 用量与每日配额。

设备是独立工作的。没有局域网 hub，没有配套服务器，不依赖另一台机器开机。每个功能
要么设备自己完成，要么退化成明确显示的离线状态。

## 2. 硬件边界

来源：`components/bsp/include/bsp_pins.h`、`docs/hardware-design/AI_HARDWARE_DEVELOPMENT_GUIDE.md`、
`README.md` 能力契约表。

| 项目 | 事实 | 后果 |
| --- | --- | --- |
| 主控 | ESP32-C3，8 MB Flash，无 PSRAM | 全部挤在内部 SRAM；Wi-Fi、TLS、LVGL、音频互相争抢 |
| 屏幕 | ST7789 240×320 竖屏 RGB565，LVGL 9，24 KB 池 + 单个 9.6 KB DMA 缓冲 | 一屏行情放得下；不能双缓冲，不能大图 |
| 按键 | UP / DOWN / OK 共享 GPIO0 ADC 电阻梯 | 回调不得阻塞；网络工作放 worker 任务 |
| 音频 | ES8311 I2S 全双工，demo 录音缓冲约 96 KB | 音频与全量联网不能同时常驻 |
| 无线 | Wi-Fi 2.4G STA 与 NimBLE 同芯片，但 RAM 预算不允许同开 | 联网（STA）与配网（SoftAP）是两个模式，不同时运行，由 `wifi_radio_owner` 强制互斥；配网全程不启用蓝牙 |
| 电池 | CW2017 电量计 | Wi-Fi 持续轮询需要睡眠策略 |

上游自己的规则（`AI_HARDWARE_DEVELOPMENT_GUIDE.md`）要求：添加网络、TLS、音频或素材时，
必须复查 24 KB LVGL 池、9.6 KB LCD DMA、I2S DMA、96 KB 录音缓冲、radio 栈、任务栈、
总 free heap 与最大连续块。基线明确预期衍生应用会加网络，并提供了核算清单。

## 3. 基线行为

`main/demo_wifi.c`（上游基线的扫描演示页，本仓库已删除）只扫描 AP，不关联、不保存凭证、不发任何 HTTP 请求。在 `main/` 与
`components/` 中检索不到 `esp_http_client`、`esp_tls` 或 JSON 解析器的使用。

联网、凭证存储、HTTP、TLS、JSON 解析全部由我们实现。好消息是 `esp_http_client`、
`esp-tls`（mbedTLS）、`nvs_flash`、`esp_ping`、`mdns`、`json` 都是 ESP-IDF 5.5.3 内置组件，
不需要新增受管依赖。

## 4. 功能评估

### 4.1 多地点 Wi-Fi profile：可行，风险最低

机制，只用内置 API：

1. NVS 里存 N 个 profile：`{name, ssid, password, location}`，外加 `active_index`。只记"哪个连上了"，
   不记"什么时候连上的"：设备没有 RTC，时间戳跨重启就没有意义，而状态机唯一需要的输入
   就是 `active_index`。
2. 开机先试 `active_index`；失败则按列表遍历，每个 profile 约 10 秒超时；全部失败后停在状态页显示原因，等用户长按 UP 进配网。
3. 断线时重跑整个遍历，而不是只重试上一个 SSID，这样人从家到公司，设备跟着换网。
4. 配网走 SoftAP，**不用蓝牙、不依赖任何小程序**：板子起一个开放热点（无密码、单客户端、信道 1）并开一个最小网页表单，手机浏览器
   提交 SSID 与密码；设备不做 APSTA 预验证，表单合法即写入 NVS 并重启，由开机遍历验证。
   不做弹窗认证（captive portal）：三键加小屏足够显示热点名与地址，而弹窗认证在不同
   手机上的探测行为差异很大，验证成本高、收益低。
5. 预设凭据作为"第一次怎么连"的种子，见下。
6. 每条 profile 携带一组坐标与地点名（记录 v3；v2 仍可读）。连接哪个网络，天气就用哪个
   地点；没填坐标的网络在天气页显示 `Location not set`。配网表单的经纬度可选、但必须成对。

状态机是纯逻辑，按上游规则必须抽出来做主机测试。这与参考应用 `xiaonuo-jianlu` 的做法一致。

**预设凭据：只解决第一次，不解决换网。** 固件可以携带个人 Wi-Fi，条数上限是
`WIFI_PROFILE_MAX`（8）：

- 开机加载 profile 库；**库为空时**把预设写入库（`add` 后 `save`），此后它们就是普通记录，
  按正常规则参与遍历。空库时 `add` 会自动把第一条设为 active，所以预设一的优先级最高。
- 库非空时什么都不做。用户删光全部网络等于"恢复出厂"，下次开机会重新注入——这是刻意的语义。
  不引入"已注入过"标志位：那类没人读的字段刚在 2026-10-29 清理过一次，不该再长回来。
- **预设永不与既有记录合并**：注入的前提就是库为空，所以不存在"与用户记录冲突"这种情况。
  唯一可能撞车的是同一份预设文件里两行写了同一个 SSID，先出现的一条胜出，后者跳过。
- 单条字段非法（SSID 空或超 32、密码超 64、显示名超 23）只跳过那一条，不让整台设备变成零网络。

机制：预设值与股票自选表一起放在 `main/app_config.local.h`，该路径必须列入 `.gitignore`
（且必须在文件第一次创建之前就提交 ignore 条目，否则一旦进过 index 就永久被扫描）。
被跟踪的 `main/app_config.h` 只声明访问器契约；`__has_include` 的兜底落在
`main/app_config.c`，这样凭据只会编进一个编译单元，测试与服务层都看不到。
`wifi_presets` 只保留注入行为。不选 Kconfig，是因为 Kconfig 没有数组，且密码里的
`$`、`"`、`\` 需要转义，容易写错。

三条边界：

- **个性化。** 预设值只能是开发者自己的网络。不得写入公司、学校、客户或他人的真实凭据，
  也不得为了"方便测试"提交一个公共网络的账号。
- **不进版本库。** 本地头文件被忽略，CI 上不存在，因此 CI 构建出的固件不带任何预设，
  仓库里也永远查不到这几个字符。
- **不是安全边界。** 字符串会以明文进入固件 `.rodata`，拿到设备就能提取。预设的作用是
  "免配网"，不是"藏密码"；真正保护凭据需要 NVS 或 Flash 加密，本期不做。文档与界面都
  不得暗示预设能保护密码。

### 4.2 天气：可行，最简单的联网功能

一次 HTTPS GET，返回很小的 JSON（当前天气约 0.5 KB），用最小字段提取解析进有界静态缓冲。

已定：**Open-Meteo**（`api.open-meteo.com`，无 key）。请求
`current=temperature_2m,weather_code&timezone=auto`；`timezone=auto` 让返回的观测时间
直接是当地时间，省掉一份时区表。地点取当前 active profile 的坐标。
选无 key 接口的理由：不必为一条密钥再建一条配网路径；带 key 的免费额度（如和风天气）
会把密钥留在 NVS 里，还要为它设计编辑与撤销。

节奏：只在天气页可见时取数，成功后 10 分钟一次，失败按 30 秒起指数退避、封顶 5 分钟。

### 4.3 股票行情：可行，数据量是约束重点

自选表：中证 AI 指数、AI ETF、纳指 100、标普 500、英伟达、特斯拉、现货黄金、镁光。

8 个标的走一到两个请求就是几 KB JSON，静态流式缓冲装得下。界面：240×320 竖屏一屏
放 8 行「名称 / 价格 / 涨跌幅 / 涨跌额 / 成交额」。

数据源选项，按优先级：

- **无 key 公开行情接口。** 常见的中国市场数据源会返回紧凑 JSON 或分隔文本，HTTPS 无鉴权。
  需要先验证响应大小、编码和限频，再定案。
- **带 key 的 API（iwencai 等）。** 数据更全，但 key 必须配进 NVS 且绝不入库，
  等于要为「一个密钥」多做一条配网路径。

这个决定只影响客户端层，可以推迟到显示和轮询调度验证通过之后再定。

轮询调度是纯逻辑（A 股与美股的交易时段、非交易时段退避），必须主机测试。

### 4.4 局域网探针：收窄定义后可行

- 用 `esp_ping` 对一小份已知端点做 ICMP 可达性检查，成本很低。
- 用内置 `mdns` 组件浏览广播的服务。
- 拒绝全 /24 网段 TCP 端口扫描：2.4 GHz 上单次 TCP 探测约 100~300 ms，扫一轮要几分钟，
  屏幕也无法有效呈现结果，还会抢占音频和 TLS 的内存预算，在本产品里没有价值。

明确范围：「我关心的端点在不在，这个网络广播了什么服务」。端点列表由用户在 NVS 里编辑。

### 4.5 AMD Radeon Cloud 用量与配额：可行，一次带认证的 GET

目标：一个产品页，显示今天 Token Factory 已用掉多少每日额度、还剩多少、什么时候重置，
以及今天的请求数、token 数与错误数。数据来自开发者自己的 API key。

下表每条事实都在 2026-11-10 从官方文档读到（文档最后更新 2026-11-03），页面地址见 §10。

| 事实 | 对设计的后果 |
| --- | --- |
| `GET https://developer.amd.com.cn/radeon/api/v1/usage`，用 API key 认证，仅中国站 | 网关前缀 `/radeon/api` 是地址的一部分。文档说去掉前缀的 `/v1/usage` 是同一个端点；客户端采用带前缀的形式，也就是文档自己 curl 里写的那条 |
| `Authorization: Bearer rc-...` | `net_http_get()` 现在只设一个固定的 User-Agent，别的一概不支持。必须先加上"请求头列表 + 状态码出参"，这个端点才有可能被调用；这是本功能对既有代码唯一强制的接口改动 |
| `daily_cost_limit_usd`、`daily_cost_used_usd`、`daily_cost_remaining_usd`、`daily_reset_at`、`daily_reset_timezone`、`today.{requests,errors,total_tokens,prompt_tokens,completion_tokens,cost,last_request_at}`、`last_30_days.{requests,total_tokens,cost}`、`all_time.*`、`by_model[]`、`recent[]` | 页面要显示的东西全部在第 0 或第 1 层，落在 `json_field` 现有上限内（4 段、64 字节路径）。`by_model` 与 `recent` 是数组，提取器把数组当不透明值跳过，不写第二个解析器就取不到，v1 两个都不显示 |
| `_usd` 后缀的单位是 Token Factory points，不是货币。文档强调了两遍，这些值与账户 credits 无关 | 页面单位写 `pts`，绝不出现 `$`。写成美元会直接说错余额，而这正是这个页面唯一要报的东西 |
| `daily_cost_limit_usd` 按账户、且随时间变化；`rpm_limit` 按 key | 上限不能编译进固件，每次都用最近一次响应里的值；上限字段缺失按"未知"处理，不按 0 处理 |
| 每日周期是北京时间的自然日；`daily_reset_at` 带 `+08:00` 偏移给出准确时刻 | 从 `daily_reset_at` 里截出钟点显示。倒计时需要"带偏移的 ISO-8601 → epoch"的日期运算，而重置永远是 00:00，不值得 |
| `401` 同时覆盖"没带请求头"和"key 被拒"，`429` 带 `Retry-After`，`502`/`503` 是暂时性故障，错误体还有两种信封（`error` 或 `detail`） | 页面要把"key 被拒""被限流""服务不可用"分开说。这三者的区分就是"卡片为什么是空的"的完整答案，一个笼统的失败码承载不了 |
| `include_recent` 默认 `false` | 不传这个参数。`recent` 是报文里唯一没有上界的一段，屏幕也放不下请求级明细 |
| 报文大小：文档示例实测压缩后约 0.6 KB、带缩进约 0.8 KB（含 `by_model`） | 现有 4 KB 共享缓冲余量很宽。截断按解析失败处理并单独提示，绝不显示半份数字 |

决策：每次取数只发一条带认证的 GET，用现有字段提取器解析成 `app_data` 总线上的第二条记录，
渲染成产品页环里新的一页：状态 → 天气 → 用量 → 状态。这条记录只活在本轮会话的 RAM 里，
持久化的取舍见下文。

v1 的非目标（为了这一段可评审）：

- 不做按模型拆解。`by_model` 是数组，提取器不下钻数组，屏幕也放不下八个模型。
- 不做 `recent` 请求列表，不做 `all_time` 累计。
- 不做倒计时、不做图、额度见底不告警。页面只报数，不对数做任何动作。
- 不在设备上编辑 key。key 是编译期的，与 §4.1 的 Wi-Fi 预设完全一致；换 key 就是重新构建、重新烧录。

节奏：沿用天气页的 10 分钟间隔，不改。配额由服务端计量，只有账户发起模型调用才会动，
而本设备不发模型调用；这个页面是监视器，不是流量计。每小时 6 次请求远低于文档给出的两个
上限（每 key 30 rpm，每账户 20 rpm）。

**key 的处理。** key 是机密，处理方式与预设同一套，没有例外：

- `APP_CONFIG_AMD_KEY` 放在 `main/app_config.local.h`，该文件被 git 忽略。入库的
  `app_config.h` 只声明一个返回 `const char *` 的访问器（该段缺失时返回 NULL），
  `app_config.c` 仍然是唯一 include 本地头文件的编译单元。
- key 以明文进入 `.rodata`，拿到 flash dump 就能提取。这不是安全边界：它把 key 挡在版本库外，
  挡不住从设备上读出。代码与界面都不得暗示相反。
- CI 构建没有 key。此时页面显示 "Key not configured"，并且不打开任何 socket。
- key 不出现在 URL 里，所以请求 URL 仍然可以安全写日志；它只出现在一个请求头里。任何日志
  都不得打印该头的值，`net_http` 保持它现有的"不打日志"性质。
- `tools/check_repo.py` 的 `SECRET_PATTERNS` 增加一条 `rc-` key 形态的规则，key 一旦被提交到
  任何位置都会让静态门禁失败。规则要求前缀后至少 20 个 ASCII 字母数字，因此文档里的打码示例
  与模板里的占位符都不会命中。

**网络层要改什么。** 天气这一段天生是单数据源：一份调度、一个可见标志、一个刷新标志、
一份快照、一条状态记录。加第二个源需要三处拆分，且每处都能在主机上测：

1. `net_http_get_ex()` 接收请求头列表与可选的状态码出参；`net_http_get()` 变成不传两者的
   薄包装，于是天气路径与它现有的测试完全不动。HTTP 桩必须记录请求头，否则这件事根本没法测；
   它现在是把头丢掉的。
2. `net_schedule` 本身不用改，结构体已经自包含，再开一个实例即可。要改的是 worker：
   可见性按源分开、刷新按源分开、每轮循环最多取一个源，这样 4 秒的停止预算仍然只覆盖
   一次在途 TLS 会话。
3. `app_data` 在 `weather_state_t` 旁边加 `usage_state_t`。一条总线、一个临界区、每条记录
   各自一个 `seq`；任一 seq 变化，UI 就重画。

`main.c` 要做同样的处理：它的页环切换现在只写了两个页的特例（状态→天气、天气→状态），
在第三页出现之前必须收成一个 `page_switch(page_id_t)`，否则六种切换会变成六个分支。

**持久化：天气留快照，用量不留。** 这两者刻意不对称。天气快照的作用是填住"唤醒到首次取数
成功"之间的那几秒，而昨晚的温度仍然大致正确；页面会给它标 `Offline - saved` 并打印取值时刻。
用量额度在北京时间 0 点归零，所以跨夜带过来的记录不是"旧"而是"错"，而错的余额比空卡片更糟，
因为用户会照着它行动。要抑制这个错误就得在 `+08:00` 偏移上做跨天运算，而做这些只为藏起一个
根本不该写进去的值。因此用量只活在 `app_data` 的会话作用域里：重启后显示 `Updating...`，
直到首次请求返回。这也让 `net_snapshot_store` 保持单一职责，不需要通用 blob 层。

**显示。** 240x320 竖屏，沿用既有产品壳，不引入新的视觉语言：

| 行 | 内容 | 数据来源 |
| --- | --- | --- |
| 页眉 | `AI PASSPORT` 与电量 | 现有 `ui_product_header` |
| 标题 | `AMD Cloud` | 静态 |
| 主卡 | 剩余点数，2 位小数；不足 1 点时保留 4 位，避免 `0.0032` 显示成 `0.00` | `daily_cost_remaining_usd` |
| 卡内明细 | `1.84 / 10.00 used` 加一条 2 px 已用/上限比例条 | `daily_cost_used_usd`、`daily_cost_limit_usd` |
| 一行 | `Reset 00:00` | `daily_reset_at` |
| 一行 | `Today 142 req  88.2k tok  3 err` | `today.*` |
| 一行 | `30d 39.77 pts` | `last_30_days.cost` |
| 页脚 | `OK refresh   UP/DOWN page` | 既有约定 |

点数以 1e-4 点的定点整数存储，与接口返回的 4 位小数对齐，因此解析器之后不再有浮点数；
量程约 21.4 万点，任何合理上限都装得下。token 数用整数运算缩写成 `88.2k` 这种形式，
设备端不做浮点格式化。`usage_format_points()` 与已用/上限百分比都是纯函数，有主机测试。

**失败时显示什么。** 最后一次成功取到的数字连同时间戳留在屏幕上，与天气页的行为一致。
失败只重发状态字段，所以 key 被拒不会擦掉它当时正在显示的那份配额。状态行区分：
未配置 key、key 被拒（401/403）、被限流（429）、服务不可用（5xx 或传输层）、响应被截断。
`usage_view_state()` 及其转移表有主机测试；只有屏幕上的字形要等上板实测才谈得上验证。

**内存代价。** 不新增任务、不新增栈、不新增缓冲：同一个 worker、同一块 4 KB 报文缓冲、
同一时刻一条 TLS 会话、取数严格串行。新增的只有总线上一条 `usage_state_t`（约 72 字节）
与页面自己的 LVGL 对象。heap 水位照例随 P5 的上板实测记录。

## 5. 架构：纯设备侧

```
[AI Passport]
  Wi-Fi profile 管理器（NVS + 状态机）
        |
  worker 任务：HTTP/TLS 客户端，有界静态缓冲，JSON 解析
        |
  数据模型（天气/用量/行情/端点状态）驻 RAM，最近一次快照进 NVS
        |
  LVGL UI 任务（每次访问都持有 bsp_lvgl_lock）
```

没有 hub 之后衍生出的设计规则：

- 凭证（如果有）只放在 NVS 记录或 git 忽略的本地头文件里，绝不入库，也不进对外发布的镜像。
- 每个网络功能持有自己的小缓冲，在开机 heap 健康时分配。
- 任何功能都不得阻塞 LVGL 任务或按键回调。
- 离线行为必须显式：显示 NVS 里的快照，并带上明显的过期标记与快照时间。快照不记录它属于
  哪个网络，所以只在"没有连接"或"当前 profile 有地点"时展示；已连上但没配地点是
  `Location not set` 的终态，绝不回放别的网络的数据。
- 路由器不转发多播时，mDNS 发现必须退化为缓存的直连地址（RFC 6762 第 8.1 节）。
  这是参考应用里记录过的已知故障模式。

## 6. 中文显示

默认 Montserrat 没有中文字形；UTF-8 编译通过不代表能显示。两条路线：

- **A（推荐）：** 用 `lv_font_conv` 从 Noto Sans SC 生成覆盖 GB2312 的子集（16 px 约 7000 字形），
  生成的 C 文件入库。8 MB Flash 放得下。
- **B：** 只收应用里出现过的字。体积更小，但每加一句文案都要重新生成。

选 A：行情名称和天气词都是中文，每改一个字就重生成字体是长期成本。

## 7. 内存纪律

1. 开机预分配 LVGL 池、音频 DMA（若启用）、HTTP 缓冲。
2. 网络、存储、音频全部在 worker 任务里。
3. 联网（STA）与配网（SoftAP）是两个模式，不同时运行，由 `wifi_radio_owner` 在启动时强制：
   抢不到射频的服务直接拒绝启动。配网期间 AP、DHCP 与 HTTP 服务共同占用内部 RAM，是本项目
   内存最紧的一段；参考实现的 13 / 31 KiB 取自 APSTA 场景，这里不用 APSTA，只能当上界看。
   进入配网页面前必须先停常驻联网服务（`main.c` 的 `services_pause()`）。
4. 每完成一个功能，在交付报告里记录 free heap 与最大连续块。
5. 加第二个网络数据源不新增任务、栈或缓冲。worker 每轮最多取一个源，4 秒的停止预算因此
   仍然只覆盖一次在途请求，TLS 峰值保持单会话。

参考应用 `xiaonuo-jianlu` 在相同硬件与 IDF 版本上的实测：Wi-Fi 驱动常驻后剩约 42 KB heap，
NimBLE 栈需约 58 KB，音频 + Wi-Fi + HTTP + UI 组合稳态约 33 KB，音频 DMA 在开机时预分配
（后期分配曾导致冻结）。SoftAP 的 13 / 31 KiB 数字来自 `phoenixzhc` 的资源预算记录。
选 SoftAP 而非 BLE 的一个附带好处：配网路径完全不加载 NimBLE，那 58 KB 不会同时压上来。

## 9. 待决问题

1. ~~天气数据源~~ 已定：**Open-Meteo**（无 key），地点取 active profile 的坐标（2026-11-01）。
2. 股票数据源：无 key 接口够用，还是带 key API 值得额外的配网成本？
3. 音频：本期做，还是等网络栈稳定后另开一期？
4. 探针清单：除了 mDNS 发现，是否需要显式的 ICMP 目标列表？
5. 配网入口的触发方式已定：**只在状态页长按 UP 手动进入**。自动进入被放弃——预设失效时那会在
   每次开机都把用户推进配网，而状态页已经把"没有网络"与提示行写在屏幕上，手动入口并不难发现。
6. 配网用 **AP-only**，不做 APSTA 预验证：表单合法即落盘并重启，由开机遍历验证。代价是密码
   错误要等一次重启才知道；收益是不必同时维护 AP 与 STA 两个接口。AP-only 下的堆水位本仓库
   尚未实测，见 §7。
7. SNTP 已定：TLS 证书有效期要求可信时间，连上 Wi-Fi 后校时；时间无效时不发起请求，
   也不关闭证书校验。快照落盘按"内容变化或满 30 分钟"节流，避免 24 KB NVS 被写穿。
8. 配置自检已定：开机检查本地配置并逐条打日志（Wi-Fi 字段、坐标、地点名、自选表、
   重复项、条数上限）；天气取值收紧到 ±100 °C 与 WMO 0–99，2xx 响应若声明了非 JSON
   的 Content-Type 按失败处理（缺头时交给解析器）。
9. `GET /v1/usage` 本身要不要计入每分钟额度？文档只说列模型会，对这个端点没说。两种答案下
   每小时 6 次都远低于所有已知上限，所以这条待决改的是文档措辞，不是行为。
10. `developer.amd.com.cn` 的 TLS 证书链是否在 ESP-IDF 的证书 bundle 里，未上板验证之前
    无从判断。若不在，做法是固定一张 CA 证书，绝不关闭校验。
11. key 轮换：单个个人 key 用"重新构建 + 重新烧录"可以接受。若嫌麻烦，下一段就是 NVS 记录
    加一个配网字段，那之后 key 要按 Wi-Fi 口令的同一套规则处理。
12. 没有 key 的构建仍然显示用量页，文案是 "Key not configured"。藏掉它会让页环顺序随构建
    变化，而天气页已经用 "Location not set" 立了先例。
13. 用量**不做持久化**，2026-11-14 定。日额度在北京时间 0 点归零，所以第二天早上读出的 NVS
    副本报的是一个已经不存在的余额，而用户会照着这个数字行动。取消它还顺带删掉一套版本化
    布局、一层通用 blob 存取，以及只为"决定何时藏起这份副本"而存在的跨天运算。天气继续保留
    快照：它填的是唤醒到首次取数之间的空档，会标 `Offline - saved`，而前一晚的温度仍然大致成立。
